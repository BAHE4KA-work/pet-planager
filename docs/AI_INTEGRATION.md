# AI integration

All generative work runs through the Tauri `ai_request` command. The renderer calls the service functions in `src/services/ai.ts`; analysis, interview, answer, and transformation requests pass the currently selected non-secret provider configuration so unsaved model/provider edits take effect immediately. The native layer reads the matching provider-specific secret, applies the saved usage limits, makes the provider request, and returns parsed data with provider/model, usage, and latency metadata. Provider keys are not passed into the renderer request, project files, or AI prompt. The connection test intentionally uses the saved configuration because Settings saves before testing.

The command input is `ai_request({ request: { action, prompt, systemInstruction, schema?, providerConfig? } })`. The optional `providerConfig` contains only `provider`, `geminiModel`, `customEndpoint`, `customModel`, and `chatgptModel`; it never contains credentials. Supported actions are `analyze`, `interview`, `interview_answer`, `transform`, and `test_provider`. Analysis, interview, answer, and transformation requests include the relevant `.pgr` records and exact line citations. When the user selects one or more elements, analysis and interview send only those elements and their citations; with no selection, they use the whole project. Previously saved interview answers are included only when relevant to the selected context. The AI may cite only the records in its request. Renderer-side runtime validation rejects malformed JSON, unknown element references, unsupported patches, invalid transformations, and citations absent from the generated range index. Deterministic graph/schema diagnostics remain available offline and are merged with provider analysis.

The renderer validates returned relation ownership and targets, unique transformation IDs, and the resulting graph before returning AI changes. PGR parsing rejects unsupported element headers, invalid or duplicate IDs, unknown header properties, and unsupported statuses with a block-specific error rather than coercing them into another element type. Gemini model choices follow the [official Gemini API model catalog](https://ai.google.dev/gemini-api/docs/models); the default is the stable `gemini-3.8-flash`, and settings migrate the retired `gemini-3.1-flash-lite-preview` ID to `gemini-3.1-flash-lite`. Gemini and custom endpoint API keys use separate Windows Credential Manager entries; an existing legacy key is migrated once to the provider selected in saved settings.

The renderer service contract is:

- `analyze({ elements, selectedIds, files, config, customGoal?, locale? })` returns proposals, contradictions, provider, and model.
- `interview({ elements, selectedIds, files, answers, config, locale? })` returns provider-generated questions.
- `applyInterviewAnswer({ targetElement, existingElements, question, answer, config, locale? })` returns a validated patch and provider summary. Pass the complete current element graph as `existingElements`; the service rejects targets absent from that graph and checks the merged graph before returning the patch.
- `transform({ sourceElement, targetPattern, existingElements, config, locale? })` returns validated new elements for `system_pack`, `class_hierarchy`, or `process_chain`.
- `testProvider(locale?)` sends a small live provider check. Settings saves first; the native command tests the currently saved provider configuration.

Provider failures are surfaced to the caller. The renderer does not create sample proposals/questions, claim an answer was applied, fabricate usage, or substitute a local result for a failed provider request. The native layer owns actual provider usage and explicit usage simulation records.

## Official ChatGPT plan provider

For the Apache-2.0 open-source desktop app, users can explicitly connect ChatGPT from Settings. The native OAuth commands (`openai_connect`, `openai_status`, `openai_models`, `openai_sign_out`) perform the documented dynamic client registration and loopback authorization-code flow with PKCE, state, nonce, verified ID-token signature/claims, and the `chatgpt.tokens.use.direct` grant. Token credentials stay in Windows Credential Manager; only connection state, account label, and the selected model reach the renderer.

The model list comes from the signed-in account’s public `/v1/models` catalog and includes displayable models only. Inference uses only `POST https://api.openai.com/v1/responses` with `store: false` and `stream: true`; a request succeeds only after `response.completed` and uses the response’s actual input/output token counts. No ChatGPT backend API is used. This flow follows the [official open-source sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [model and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), and [account/session](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) guidance.

Failed calls with unknown provider usage retain the original conservative token reservation. Rate-limit totals and the Settings usage view charge/display that reservation rather than silently counting the failed request as zero; the event marks usage as unknown so it is distinct from measured tokens.
