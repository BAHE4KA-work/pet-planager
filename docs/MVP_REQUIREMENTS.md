# Planager MVP acceptance and delivery plan

This document turns the concrete product behaviors in `docs/INVESTOR_KNOWLEDGE_BASE.md`, the README, current UI, model types, and utilities into a full-scope acceptance checklist. It is a target definition, not a claim that the current prototype implements the behavior. Marketing claims and monetization directions are identified separately so they are not mistaken for MVP requirements; they do not remove any concrete feature from scope.

## Product boundary

The delivered application is a desktop Tauri application that manages real local project files, has no mock/sample activity presented as user data, and retains every concrete workflow already declared in the investor knowledge base and implemented or exposed in the prototype. Existing example projects may remain importable examples, clearly labeled as such. The feature surface must use reusable, consistent UI patterns across the knowledge base, canvas, assistant, library, and settings.

Optional provider sign-in may use the officially documented open-source Sign in with ChatGPT OAuth flow, because this application is distributed under Apache-2.0. Do not use undocumented ChatGPT backend endpoints or imply that OAuth authorizes unrelated Codex product APIs. Gemini and configured custom endpoint behavior remain supported AI providers.

## Claims that are not separate MVP deliverables

The investor document also contains market-problem estimates, comparisons, “enterprise edition” positioning, hardware acceleration, and future monetization (B2B SaaS, on-premise enterprise deployment, AI credits/gateway marketplace). These are positioning or business directions, not concrete end-user workflows. MVP still must satisfy the concrete local desktop, authoring, graph, AI, versioning, limits, and UX behaviors above. Do not add SaaS billing, multi-tenant collaboration, marketplace, or enterprise deployment as new product features in this migration.

## Delivery waves and ownership

Waves are bounded by deliverable and ownership. Keep UI components reusable; avoid further concentration of product logic in `App.tsx`.

1. **Tauri foundation and real workspace persistence.** Own Tauri config/native commands, app entry/build scripts, workspace service and persistence boundaries. Migrate project lifecycle and file/folder actions off Express/browser APIs; ensure startup, open/create, save/reopen, import/export and failure handling work with a real local workspace. Start with real workspace data and no preloaded project fixture.
2. **PGR and editing correctness.** Own `pgrCodec`, model validation, editor state/history, reusable KB/editor components, and inspector. Complete round-trip editing, syntax feedback, range handling, inheritance, references, undo/redo, and multi-file operations.
3. **Canvas and shared interaction system.** Own canvas/layout/edge/selection modules and shared UI primitives. Complete canvas interaction promises, radial menu, accessibility, and consistency across surfaces; keep graph and source changes synchronized.
4. **AI workflows without mock behavior.** Own provider configuration/call boundary, response validation, assistant workflows, and optional official OAuth evaluation. Preserve deterministic local diagnostics; remove fake generative fallbacks and route every proposal/interview/transformation/fix through configured provider or clearly identified deterministic capability.
5. **Git and reusable units.** Own native Git/workspace integration, commit/branch/diff UI, and library persistence/import. Replace in-memory pretend snapshots and starter library state with actual repository/library operations.
6. **Usage safeguards, localization, and product polish.** Own real usage event schema/limiter/settings analytics and shared localization/theme/accessibility cleanup. Replace randomized metrics, add explicit simulation mode, and finish consistent loading/error/empty states.

Each wave owns its implementation files and interfaces; shared contracts (`PlanElement`, PGR services, workspace commands, usage records, and UI primitives) must be agreed before parallel implementation. `src/App.tsx` should be split as each domain is migrated rather than treated as a single-file feature owner. Run the existing typecheck/build commands after implementation changes; this requirements-only change does not claim runtime verification.

## Product questions

No product-author decision is required to define this checklist. Implementation may choose sensible defaults for supported desktop platforms, default workspace location, local Git library, and token-window semantics, documenting them in-app where relevant. Official open-source Sign in with ChatGPT OAuth is in scope for the Apache-2.0 app and is implemented through the documented public flow. The app currently stores one active registration; switching through the UI explicitly removes that registration before connecting another account.
